# Container log browser

`Platform / Container logs` uses the existing VictoriaLogs (DS) datasource and
Grafana Operator. It references the chart's stable datasource UID `VictoriaLogs`
(the display name is `VictoriaLogs (DS)`). Adapt that UID for other stacks. Namespace, Pod and container dropdowns query live Kubernetes
metadata fields; level and message-regex filters narrow the selected time range.
The panel returns at most 1000 records. Use Explore for further LogsQL queries.

The shared VictoriaMetrics stack enables vlagent's native Kubernetes collector.
The operator replaces the push-only StatefulSet with a DaemonSet, including the
control plane. Each agent reads its node's container runtime logs and enriches
records with `kubernetes.pod_namespace`, `kubernetes.pod_name`,
`kubernetes.container_name` and node metadata. JSON messages are parsed by vlagent;
plain messages retain their runtime timestamp and stdout/stderr stream. Metadata
RBAC and read-only host log mounts are generated by the operator.

`/var/lib/vlagent-data` is a writable DirectoryOrCreate hostPath for checkpoints
and remote-write buffering. The buffer is capped at 128 MiB per destination per
node. No template-specific remote-write throughput limit is imposed. It survives agent restarts on that node, not playground destruction. A long
backend outage can cause bounded-buffer loss. This is not an audit log archive.
The lab retains backend logs for two days in a 2 GiB PVC; inspect capacity and
adjust retention/storage before collecting sustained high-volume logs.

Existing pushed SDK logs still reach the same service. They may lack Kubernetes
metadata, so they are intentionally outside this container-log browser. An SDK
record and an application stdout copy are different ingestions and can both exist.
Logs written only to arbitrary files inside a container are not collected.

All panels share namespace, Pod, container, level and message filters. Summary
cards count matching records, errors/fatals, warnings and unknown levels over the
selected time range. A time series splits volume by normalized level; tables rank
the top 20 service/level groups and exact recurring messages. These aggregations
cover the full query range, independent of the log viewer's 1000-record cap.

The level selector uses the first nonempty value from `level`, `severity_text`,
then `severity`. Case is normalized; WARNING becomes warn, ERR becomes error,
and CRITICAL/PANIC become fatal. Missing or unrecognized values become `unknown`,
which can be selected alone or alongside other levels. All includes every level.
Original fields remain intact; `log_level` is a query-time derived field.
Plain text is not guessed to be INFO, and stderr is not automatically ERROR.
Service grouping uses `service.name`, then the Pod's app.kubernetes.io/name or app
label, then container name, and retains namespace to separate equal names. It
identifies application groups, not discovered Kubernetes Service objects. Recurring
messages are exact text matches; variable IDs and embedded timestamps remain
separate. Use shorter time ranges for high-volume namespaces.

Expand log details to see original structured fields. Namespace access in
this dashboard is filtering, not authorization: users of this datasource can
query all collected namespaces. Avoid logging secrets in applications.

## Live deployment findings — 2026-11-01

The collector ran on all three nodes in the rebuilt play. Backend field-value
queries returned logs from all three node names and 11 infrastructure namespaces
in a five-minute sample. Parsed levels included info/warn/error and uppercase
variants, alongside unclassified plain-text records. The exact dashboard query
with kube-system, etcd Pod/container and WARN filters returned matching records
with the expected node and stderr fields.

During the first backfill the API timed out and `/readyz` temporarily reported
etcd trouble. It subsequently returned `ok`. Native agent logs reported retries
to the backend during the slow interval. At that time, a temporary write-rate cap bounded backfill
pressure; it was not proof that initial backfill caused every API slowdown.
The control-plane sizing and existing root-disk pressure limitations still apply.

The log viewer defaults to single-line messages with inline labels hidden. Expand
a row to inspect metadata and structured error fields. This keeps the timeline
compact without deleting fields from storage. See the dated
[error review](../../docs/findings/log-error-review.md) for examples of generic
messages whose useful cause is in `err` or `error`.
